CORE OOP PRINCIPLES
================================================================================

1. ENCAPSULATION
----------------

Definition: Bundling data and methods within a single unit (class), restricting 
direct access to components.

Implementation:
- All model fields are private
- Public getters and setters provide controlled access
- Business logic encapsulated in methods

Example from Account class:
  private String uid;
  private String firstName;
  private String lastName;
  private String email;
  private UserRole role;
  
  public String getUid() { return uid; }
  public void setUid(String uid) { this.uid = uid; }

Example from AuthMeta class with business logic:
  public boolean isAccountEnabled() {
      return !isAccountExpired() && !isAccountLocked();
  }

2. INHERITANCE
--------------

Definition: Mechanism where a new class derives properties and behaviors from 
an existing class.

Class Hierarchy:

Account (Base Class)
  - TeacherProfile (extends Account)
  - StudentProfile (extends Account)

Account contains common fields:
  - uid, firstName, lastName, email, role, bio, profileImageUrl

TeacherProfile adds teacher-specific fields:
  - inviteCode, hourlyRate, rating, tytCourses, aytCourses

StudentProfile adds student-specific fields:
  - gradeLevel, teacherIDs
  - addTeacherID() method
  - removeTeacherID() method

Benefits:
- Code reuse for common user attributes
- Logical "is-a" relationships
- Easy to extend with new user types
- Supports polymorphism

3. POLYMORPHISM
---------------

Definition: Ability of objects to take on multiple forms, allowing different 
classes to be treated through the same interface.

Runtime Polymorphism in AccountRepository:

  public Account getAccount(String uid) {
      DocumentSnapshot document = future.get();
      
      if (document.exists()) {
          String role = document.getString("role");
          
          if (role.equalsIgnoreCase("TEACHER")) {
              return document.toObject(TeacherProfile.class);
          } else if (role.equalsIgnoreCase("STUDENT")) {
              return document.toObject(StudentProfile.class);
          }
          return document.toObject(Account.class);
      }
      return null;
  }

Method returns Account type but actual object can be TeacherProfile or 
StudentProfile. This enables dynamic dispatch where correct methods are 
called based on actual object type.

Interface-Based Polymorphism:

  WebConfig implements WebMvcConfigurer
  RateLimitInterceptor implements HandlerInterceptor
  FirebaseTokenFilter extends OncePerRequestFilter

4. ABSTRACTION
--------------

Definition: Hiding complex implementation details and exposing only essential 
features.

Service Layer Abstraction Example:

RegisterService abstracts complex registration process:
  - Create User in Firebase Auth
  - Generate Custom Token
  - Create Account in Firestore
  - Send Verification Email
  - Handle Rollback on Failure

Caller only needs to call register() method - details are hidden.

Abstraction Layers:
1. Controller abstracts HTTP details from business logic
2. Service abstracts business rules from data access
3. Repository abstracts database operations from business logic
4. DTO abstracts data validation from business objects

DESIGN PATTERNS
================================================================================

1. DEPENDENCY INJECTION PATTERN
--------------------------------

Used throughout the project via Spring Framework. Constructor-based injection 
is preferred over field injection.

Example from AccountController:
  private final RegisterService registerService;
  private final VerificationEmailService verifyEmailService;
  
  public AccountController(
          RegisterService registerService,
          VerificationEmailService verifyEmailService,
          // ... other dependencies
  ) {
      this.registerService = registerService;
      this.verifyEmailService = verifyEmailService;
  }

Benefits: Loose coupling, easier testing, single responsibility compliance

2. REPOSITORY PATTERN
---------------------

Abstracts data access operations.

AccountRepository provides:
  - createAccount(Account account)
  - getAccount(String uid)
  - updateAccount(Account account)
  - deleteAccount(String uid)
  - batchCreateAccounts(List<Account> accounts)

Benefits: Centralizes data access logic, easy to swap database implementations

3. DATA TRANSFER OBJECT (DTO) PATTERN
--------------------------------------

Separates API contracts from domain models.

Example from SignUpDTO:
  @NotBlank(message = "First name is required")
  @Size(max = 64, message = "First name must be less than 64 characters")
  private String firstName;
  
  @Email(message = "Invalid email format")
  private String email;
  
  @Size(min = 6, max = 64, message = "Password must be at least 6 characters")
  private String password;

Benefits: Validation at API boundary, decouples API from domain models, 
security by excluding sensitive fields

4. SINGLE RESPONSIBILITY SERVICES
----------------------------------

Each service has one specific purpose:
  - RegisterService: handles user registration only
  - ChangeNameService: handles name changes only
  - ChangeEmailService: handles email changes only
  - VerificationEmailService: handles email verification only
  - UpdateProfilePictureService: handles profile pictures only

Benefits: High cohesion, low coupling, easier testing, better organization

5. STRATEGY PATTERN
-------------------

Used in rate limiting implementation with different strategies for different 
endpoint types.

RateLimitType enum:
  - SENSITIVE: strict limits for security-critical endpoints
  - DEFAULT: standard limits for regular endpoints

Usage:
  @PostMapping("/register")
  @RateLimit(type = RateLimitType.SENSITIVE)
  
  @PostMapping("/onboarding/complete")
  @RateLimit(type = RateLimitType.DEFAULT)

6. FILTER/CHAIN OF RESPONSIBILITY PATTERN
------------------------------------------

Used in security filter chain.

FirebaseTokenFilter extends OncePerRequestFilter:
  - Processes request
  - Verifies token
  - Passes to next filter in chain

7. BUILDER PATTERN
------------------

Used via Firebase SDK and Bucket4j:
  
  UserRecord.CreateRequest request = new UserRecord.CreateRequest()
      .setEmail(dto.getEmail())
      .setPassword(dto.getPassword())
      .setDisplayName(dto.getFirstName() + " " + dto.getLastName());
  
  Bandwidth limit = Bandwidth.builder()
      .capacity(sensitiveCapacity)
      .refillIntervally(sensitiveRefillTokens, Duration.ofMinutes(minutes))
      .build();

8. FACTORY PATTERN
------------------

Implicit factory behavior in AccountRepository when creating appropriate 
object based on role.

9. SINGLETON PATTERN
--------------------

All Spring-managed beans are singletons by default:
  @Service, @Repository, @Component, @Configuration

10. TEMPLATE METHOD PATTERN
---------------------------

OncePerRequestFilter provides template method, subclasses override specific 
steps:
  
  public class FirebaseTokenFilter extends OncePerRequestFilter {
      @Override
      protected void doFilterInternal(...) {
          // Custom implementation
      }
  }

PACKAGE STRUCTURE AND MODULARITY
================================================================================

High Cohesion, Low Coupling:

model/          - Domain entities (no dependencies on other layers)
dto/            - API contracts (validation only)
repository/     - Data access (depends on models)
service/        - Business logic (depends on repositories and models)

Dependency Direction:
Controllers -> Services -> Repositories -> Models
     |
   DTOs

Benefits:
- Clear separation of concerns
- Easy to locate functionality
- Minimal circular dependencies
- Testable layers

================================================================================
BEST PRACTICES OBSERVED
================================================================================

1. Constructor-Based Dependency Injection
   - Immutability with final fields
   - Explicit dependencies
   - Easier testing

2. Immutable DTOs
   - Only getters (no public setters)
   - Exception for password clearing (security)

3. Validation at API Boundary
   - @NotBlank, @Email, @Size annotations
   - Clear error messages

4. Proper Exception Handling
   - GlobalExceptionHandler with @ControllerAdvice
   - Centralized error handling

5. Centralized Logging
   - Custom Logger utility class
   - Consistent logging across application

6. Enum for Constants
   - Type-safe constants
   - Prevents invalid states

7. Package-by-Feature Organization
   - Related services grouped together
   - Better code organization

8. No-Args Constructor for Frameworks
   - Required for Firestore deserialization
   - Required for Spring proxying

AREAS FOR IMPROVEMENT
================================================================================

1. Interface Segregation
   - Consider interface-based dependencies instead of direct class dependencies
   - Better testability and flexibility

2. Builder Pattern for Complex Objects
   - Use Lombok @Builder annotation
   - More readable object construction

3. Stronger Type Safety
   - Consider value objects instead of primitive types for IDs
   - Prevents mixing different ID types

4. Domain Events
   - Event-driven architecture for cross-cutting concerns
   - Better decoupling

5. Custom Exceptions
   - Domain-specific exceptions instead of generic ResponseStatusException
   - Better error handling and debugging

6. Documentation
   - Add JavaDoc comments for public APIs
   - Document complex business logic
